<task type="auto">
  <name>Task 1: Compress pen3D.glb with meshopt via gltf-transform</name>
  <files>public/models/pen3D.glb, package.json</files>
  <action>
1. Install gltf-transform CLI as a dev dependency:
   ```bash
   bun add -d @gltf-transform/cli
   ```

2. Back up the original GLB:
   ```bash
   cp public/models/pen3D.glb public/models/pen3D.original.glb
   ```

3. Compress to a separate output file (do NOT overwrite in-place — risk of corruption per research pitfall #2):
   ```bash
   bunx gltf-transform optimize public/models/pen3D.glb public/models/pen3D.optimized.glb --compress meshopt
   ```

4. Compare sizes:
   ```bash
   ls -lh public/models/pen3D.glb public/models/pen3D.optimized.glb
   ```
   Expected: optimized file should be ~2-4MB (50-75% reduction from 7.7MB).

5. Replace original with optimized:
   ```bash
   mv public/models/pen3D.optimized.glb public/models/pen3D.glb
   ```

6. Start the dev server (`bun run dev`) and visually verify the pen model renders correctly in the browser. The `useGLTF` call in HeroScene.tsx should auto-decode meshopt via drei v10.7.7's built-in MeshoptDecoder support.

7. **If the model fails to load or renders as empty/broken:** In practice, drei v10 auto-wires MeshoptDecoder via `three-stdlib`, so step 6 should succeed without any manual setup. If the model is broken, the failure is almost certainly file corruption — not a decoder issue. Recovery: restore the backup (`cp public/models/pen3D.original.glb public/models/pen3D.glb`), verify the gltf-transform CLI output for errors, and retry compression. Do NOT attempt `useGLTF.setMeshoptDecoder` — that API does not exist in drei v10.

8. After successful visual verification, remove the backup:
   ```bash
   rm public/models/pen3D.original.glb
   ```

9. Ensure `.gitignore` does NOT ignore `.glb` files (it shouldn't, since pen3D.glb is already tracked).

<task type="auto">
  <name>Task 2: Lazy-load ProductIntroSection via next/dynamic</name>
  <files>src/app/page.tsx</files>
  <action>
1. Replace the static import of ProductIntroSection with a dynamic import in `src/app/page.tsx`.

   **Current code (lines 1-12):**
   ```tsx
   import HeroSection from "@/components/hero/HeroSection";
   import ProductIntroSection from "@/components/product-intro/ProductIntroSection";

   export default function Home() {
     return (
       <main>
         <HeroSection>
           <ProductIntroSection />
         </HeroSection>
       </main>
     );
   }
   ```

   **Replace with:**
   ```tsx
   import dynamic from "next/dynamic";
   import HeroSection from "@/components/hero/HeroSection";

   const ProductIntroSection = dynamic(
     () => import("@/components/product-intro/ProductIntroSection"),
     { ssr: true }
   );

   export default function Home() {
     return (
       <main>
         <HeroSection>
           <ProductIntroSection />
         </HeroSection>
       </main>
     );
   }
   ```

   **Why `ssr: true`:** ProductIntroSection is pure DOM/GSAP content (no WebGL). SSR ensures the DOM is present at first paint, which avoids ScrollTrigger timing issues (the hooks `useScrollHijack` and `useHeroScrollProgress` use ScrollTrigger and reference this DOM). The JS chunk is still lazy-loaded, but the HTML is server-rendered.

2. Run `bun run build` and check the build output — the ProductIntroSection and its children (ProductIntroBridge, FeatureAIWriting, FeatureSmartSync, FeatureFocusMode, ProductIntroCTA, SectionDivider) should appear as a separate chunk in the build output.
  </action>

  </verify>
  <done>ProductIntroSection is loaded via next/dynamic with ssr:true, build succeeds, and no scroll-related regressions (ScrollTrigger hooks still function because SSR DOM is present at first paint)</done>
